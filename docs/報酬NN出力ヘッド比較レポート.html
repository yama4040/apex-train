要約

損失関数の変更では直らなかった

主要4指標のうち3つで現行が最良でした。ただし内訳を見ると、提案①の劣化は実装上の欠陥で説明でき、真の問題は損失関数の外側にあることが分かりました。

反証

「データ数の多いラベルに引っ張られている」という仮説

支持されません。最も学習データが少ない 0.7（約 224 行）がほぼ無バイアスで、12 倍以上のデータがある 0.9 が最悪級のバイアスでした。バイアスは件数の関数ではなく値の関数です。

改善せず

提案①（HL-Gaussian）・提案②（ゼロアトム統合）

balanced-MAE・校正の傾き・収縮係数のいずれも現行を上回りませんでした。唯一、頻出ビンへの吸引率だけが 34.3% → 28〜30% に下がりました。

要再実行

提案①の劣化はビン配置の実装欠陥だった

端のラベルでガウス目標の裾が切れ、y=1.0 の教師期待値が 0.963 になっていました。校正の傾きへの寄与を計算すると −0.045 で、観測差 −0.053 のほぼ全部を説明します。修正済みのため①のみ再実行の価値があります。

比較の設計

出力ヘッドと損失だけを差し替えた統制比較

幹（128-64-32・BatchNorm・Dropout 0.3/0.2/0.1・L2 1e-4）、入力（状態 53 次元＋モード one-hot 4 次元）、データ、分割（乱数種 42・0.1 刻み層化）、スケーラ、サンプル重み、Adam の設定をすべて現行と揃え、出力層と損失関数だけを差し替えました。提案①のゲートは現行と同一のものを共有しているため、①の差分は回帰の損失のみに由来します。

既存の train_reward_network2.py・direct_reward_predictor2.py・analyze_reward_imbalance.py は変更していません。学習は train_reward_heads.py、評価は compare_reward_heads.py で行い、指標は analyze_reward_imbalance.py のものを再利用しています。

発見 01

バイアスは学習件数と対応していない

検証の主眼だった「多いラベルに引っ張られていないか」を、真値ビン別のバイアスを学習件数の順に並べ替えて確認しました。もし頻度による引っ張りが主因なら、件数が少ないラベルほどバイアスが大きくなるはずです。

学習件数とバイアスは reward_head_frequency_pull.png のパネル (a)、および reward_head_comparison.png のパネル右下から読み取った値（バイアスは ±0.005 程度の読み取り精度）。件数はラベル分布ヒストグラムの 80%（学習側）で、合計は 37,748 行と整合します。

結論：バイアスは件数ではなく「値」の関数

低いラベル（0.1〜0.5）は一様に過大評価され、高いラベル（0.8〜1.0）は一様に過小評価されています。件数との対応はまったくありません。つまり起きているのは頻度への引っ張りではなく、値の軸に沿った中央への収束です。

発見 03

提案①の劣化はビン配置の実装欠陥だった

今回の実行では提案①のビン中心をラベル範囲そのもの（0.1〜1.0）に置いていました。このため端のラベルでガウス目標の裾がサポート外に切られ、教師分布の期待値自体がラベルからずれていました。実測値です。

教師分布（打ち切り正規分布）の期待値 — ビン幅 0.1・σ=0.075
設定y=0.1 の期待値y=0.2〜0.8y=1.0 の期待値最大ズレ
今回の実行（予備ビンなし）0.137誤差ゼロ0.9630.0369
修正後（予備ビン 1・幅 0.05）0.1024誤差ゼロ0.99760.0024

中央のラベル（0.2〜0.8）は誤差ゼロで、端の 2 ビンだけが構造的に潰れていました。つまり提案①は端のラベルを原理的に当てられない設定で走っていたことになります。

この欠陥が観測差のほぼ全部を説明する

打ち切りによる摂動を真値に回帰して校正の傾きへの寄与を計算すると −0.045。観測された差は 0.739 → 0.686 の −0.053 でした。

HL-Gaussian の狙いは希薄な中央で実際に効いている

「ガウス目標が隣接ビンへ質量を分配し、希薄ラベル間で統計的強度を共有する」という Imani & White (2018) の主張どおり、0.6 / 0.7 では現行より 15〜17% 誤差が小さくなっています。端の劣化は修正可能な実装由来なので、①だけは修正版で引き直す価値があります。

発見 04

提案②はゼロ判定の専門性を失う

現行の分離ゲートはラベル 0.0 を非常に高い精度で当てています。単一ヘッドに統合すると、この専門性が明確に落ちました。

真値 0.0 における MAE（ラベル全体の約 35% を占める）
構成MAE備考
_base（分離ゲート）0.017現行。極めて良好
_hlg（同じゲートを共有）0.017ゲートが同一なので当然一致
_atom:gate（統合・ハード判定）0.041約 2.4 倍に悪化
_atom:expect（統合・期待値）0.062約 3.6 倍に悪化

期待値読み出しでは、厳密な 0.0 を出すためにアトムの確率が 1 に極めて近い必要があり、構造的に 0.0 を出しにくい側に倒れます。0.0 がラベルの約 35% を占めるため、これが balanced-MAE を直接押し下げています。

統合のメリットはコストに見合わない

提案②の利点は「閾値の不連続を消す」「モデル数を 3 → 2 に減らす」でした。しかし不連続の除去は、現行の 2 段構成のまま合成を (1 − π)·reg にするだけでも達成できます。ゼロ判定精度を 2.4 倍悪化させる必要はありません。

推奨

推奨するNN構成

現行の 2 段構成（ゲート＋回帰）を骨格として維持し、回帰器の出力ヘッドと損失、および推論時の合成の 2 点だけを変更します。幹・入力・ゲートは一切触りません。

入力 変更なし — 状態 53 次元（reward_features.STATE_FEATURE_COLS）＋ モード one-hot 4 次元 = 57 次元
モード判定も現行のまま（anti_mid_stop のみ NN、他はルール）
幹 変更なし — Dense 128 → 64 → 32、各層 BatchNorm ＋ ReLU ＋ Dropout(0.3 / 0.2 / 0.1)、L2 1e-4
Adam lr=1e-3・clipnorm=1.0
ゲート 変更なし・分離を維持 — Dense(1, sigmoid)、binary_crossentropy、停車フェーズに重み 3.0
統合しない。真値 0.0 の MAE 0.017 という現行の性能を保つため
回帰器 HL-Gaussian に変更 — Dense(21, softmax)。ビン中心 0.05〜1.05（幅 0.05・核 19 ＋ 予備ビン 各 1）、σ = 0.0375
損失は categorical_crossentropy、教師はラベル中心の打ち切り正規分布。予測はビン中心の期待値
合成 ソフト化 — reward = (1 − π(x)) · Σ fi ci
ハード閾値・clip(0.1, 1.0)・round(_, 1) をすべて撤廃。出力はヘッドが有界なので clip 不要

この構成を選ぶ理由

  • 希薄な中央値で実測の改善がある — 0.6 / 0.7 で MAE が 15〜17% 小さい。ガウス目標が隣接ビンへ質量を分配するため、頻度逆数のサンプル重みのようにノイズを増幅せずに希薄ラベルを扱える。
  • 出力が構造的に有界 — 現行の線形出力は生の値が [−0.402, +0.937] のように値域外へ出ており（テスト行の 26.7%）、clip が破綻を隠していました。softmax の期待値なら値域外が原理的に発生しません。
  • 0.1 刻みの量子化が消える — 現行の round(_, 1) と clip の下限 0.1 のせいで、報酬 0.1 が実質出力されない状態でした（DQN 実走行で 0.22%）。期待値は連続値です。
  • ゲートの不連続が消える — 閾値をまたいだ瞬間に報酬が 0 ↔ 0.5 以上へ飛ぶ現象がなくなり、DQN が受け取る報酬が滑らかになります。
  • 副産物として分散が得られる — ヒストグラムの広がりから「NN が自信を持てない状態」を検出でき、駅手前の減速フェーズで評価が 0 に張り付く問題（全ステップの 72%・そのうち 91% が 0.0）の診断に使えます。

結論

本丸はデータ側にある

推奨構成は「出力が有界になる」「量子化と不連続が消える」「希薄な中央値が少し良くなる」という工学的な改善をもたらしますが、今回明らかになった主問題を解決するものではありません。

最も学習件数が少ない 0.7 を 7 倍も過剰生産し、バイアスが件数とまったく対応していないという事実は、ほぼ同一の入力に矛盾したラベルが付いていることの帰結です。この条件付き平均は、どのような損失関数を使っても動きません。

次の一手の優先順位

1. ノコギリ運転の減点規則の適用揺れを解消して再ラベルする。適用率が 77.4%（19 ファイル）と 16.6%（26 ファイル）に二極化しており、これが 0.6〜0.7 への収束を生んでいます。

2. python analyze_reward_imbalance.py --noise-check で既約ノイズ（ベイズ誤差の目安）を測る。ラベルを直したとき balanced-MAE をどこまで下げられるかの上限が分かります。

3. 推奨構成への移行は、ラベル整合後に行う。矛盾を含んだデータで手法を評価しても結論が出ないためです。
